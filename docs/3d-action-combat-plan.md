# 固定视角 3D 即时战斗实施计划

状态：已完成，G0 至 G6 全部通过

更新日期：2026-08-20

## 1. 计划目的

本计划验证并逐步实施以下产品方向：

- 世界从当前 2D 等距像素表现迁移为固定正交视角的 3D 表现；
- 战斗从独立 `BattleGameScene` 中的回合指令，迁移为当前地图内的实时动作战斗；
- 保留传统单机修仙 RPG 的剧情、手工内容、资源取舍和持久世界后果；
- 借用暗黑式战斗的走位、攻击判定、技能循环和敌群压力，首期不引入随机词缀与刷装经济；
- 用一个可逆灰盒先验证操作、镜头、渲染和生产成本，再决定是否迁移正式内容。

本文件在 G1 通过前只是一份迁移计划，不替代 `requirements.md`、`architecture.md`、
`content-authoring.md`、`asset-pipeline.md` 和 `map-generation.md` 中的当前正式契约。G1 通过后，
进入正式实现的架构与 schema 变化必须同步这些文档。

## 2. 当前基线与约束

当前正式切片必须在迁移决策期间继续可运行：

- `map.roadside.north_slope_wilds`、`map.roadside.shop` 和 `map.roadside.herb_slope`；
- 两趟采药、路线风险、留根或连根、持久地图结果、菜单和存读档；
- Godot 4.8、静态类型 GDScript、桌面端键盘和手柄；
- `640 x 360` 根 Viewport、默认 `1280 x 720` 窗口；
- GameRoot、GameSceneStack、GameRun、ContentDatabase、StoryEvent、StoryModule、StoryContext；
- 编辑期确定性地图生成，运行时只加载已经烘焙的普通场景；
- 正式素材只来自 `assets/original/`，保持源文件、处理步骤和运行资源可追踪。

迁移不得引入 `GameSession`、`GameFlow`、通用动作数组、剧情 opcode、无边界 EventBus 或大量
Autoload。长期状态仍只进入 GameRun，地图与战斗 Node 不得成为存档数据的唯一持有者。

## 3. G0 已确认方向

以下方向已在 2026-08-18 确认。任何变更都记录在本节，而不是让实现自行漂移。

### 3.1 战斗体验

- 普通战斗直接发生在 MapGameScene，不切换到独立战斗画面。
- 键鼠默认使用左键情境操作：点地移动、点怪追击普攻、点互动对象自动接近；方向键或 WASD
  作为辅助直移并覆盖鼠标导航。手柄继续使用左摇杆直接移动。
- 鼠标位置或右摇杆提供攻击方向；没有有效瞄准输入时使用角色朝向与有限软锁定。
- 当前正式动作包括移动、普通攻击、三个主动技能、闪避和一个物品快捷键。
- 一次遭遇由一个有限敌群构成，具有明确的开始、Victory、Escaped 和 Defeat 边界。
- 敌人具有感知、追击、攻击前摇、攻击生效、恢复、受击、死亡和返回出生区域的明确状态。
- Victory 完成来源遭遇；Escaped 保留来源；Defeat 由调用方恢复队伍并转移到安全位置。
- 正式奖励继续手工配置；首期不生成随机词缀、装备品质、掉落光柱或无限刷怪。

### 3.2 视觉方向

- 摄影机使用固定 yaw、pitch 和正交投影，不允许玩家自由旋转。
- 初始镜头以当前斜 45 度构图为参照，灰盒中比较少量候选 pitch 与 orthographic size。
- 角色在 `640 x 360` 内部画面中保持约 48 至 64 像素的可见高度。
- 首选低多边形、清晰轮廓、有限色板和小尺寸手绘纹理，不追求写实 PBR。
- UI 继续使用 Control 与清晰矢量中文，不把 HUD 烘焙到 3D 世界。
- 灰盒先使用根 Viewport，不提前增加 SubViewport。只有 G1 证明根 Viewport 无法同时满足
  3D 稳定性和 UI 清晰度时才单独提出渲染架构变更。

### 3.3 首期范围

- 单个可操作队长，不实现队友战斗 AI。
- 地面移动，不实现跳跃、攀爬、飞行和多层立体寻路。
- 一种近战普通攻击、一个直线投射技能和一个近身范围技能。
- 两种敌人行为模板：近战追击与保持距离后施放投射物。
- 一种简单持续状态，按秒或固定 tick 结算。
- 战斗中禁止保存、打开商店、进入事务菜单或触发新的独占剧情。
- 暂不实现装备外观组合、复杂 ragdoll、动态破坏和联机同步。

### 3.4 2026-08-20 ARPG 操作修订

- 左键统一承担点地移动、点怪追击普攻和点 NPC/采集物/Portal 互动；按住左键可持续移动或连续普攻。
- Shift + 左键原地攻击，Ctrl + 左键强制移动；WASD/方向键随时取消鼠标导航并直接接管。
- 键鼠技能为右键、1、2，Space 闪避，Q 丹药；手柄为 A 普攻/互动、X/Y/RB 三技能、B 闪避、LB 丹药。
- MapGameScene3D 解析屏幕目标和情境，PlayerCharacter3D 通过 NavigationAgent3D 执行路径移动，
  BattleSession 仍只接收类型化意图。这一修订替代 2026-08-18 的“直接移动优先”输入结论。

## 4. 成功指标

G1 灰盒必须满足 4.1 至 4.3 的技术条件，才进入正式规则迁移。4.4 的素材生产成本条件由阶段 3
实际资产验证，并在 G3 决策门检查；它不会因为 G1 技术灰盒通过而被推定成功。

### 4.1 操作与可读性

- 键盘和常见手柄均可完成移动、瞄准、攻击、技能、闪避和物品操作。
- 玩家可以在第一次游玩的一分钟内判断敌人的警戒、攻击前摇、受击和死亡状态。
- 三只敌人同时接近时，玩家、敌人、投射物、攻击范围和地面障碍不产生难以理解的遮挡。
- 角色移动方向、瞄准方向和攻击方向没有持续互相抢夺。
- 暂停、失焦、对话和场景切换后不会残留移动或攻击输入。

### 4.2 性能与稳定性

- 目标机器在 `1280 x 720` 窗口下稳定达到 60 FPS。
- 20 个灰盒敌人的压力场景不出现持续低于 60 FPS 或明显导航停顿。
- 固定摄影机静止时没有显著几何抖动；移动时没有不可接受的边缘闪烁。
- 连续运行 20 次遭遇，不出现敌人失去归属、重复奖励、无法结束或输入无法恢复。

### 4.3 规则与内容边界

- 相同 seed、相同初始状态和相同动作输入产生相同的规则结果。
- 伤害、消耗、冷却、状态、死亡和结果提交可在无窗口测试中验证。
- G1 原型产生类型化 BattleResult；G2 正式集成证明它能驱动 StoryModule 的三个结果分支。
- 失败或取消的遭遇不完成 persistent 来源，也不发放 Victory 奖励。

### 4.4 生产成本

- 记录基础人形、六个通用动画、一件武器和一种敌人的实际制作时间。
- 第二个共用骨骼的角色或敌人变体，制作时间应明显低于第一套基础资产。
- 同一模型可在任意战斗朝向使用，不增加方向性运行资源。
- 美术源文件、导出文件、导入设置与最终场景之间能够追踪。

### 4.5 工期与资源假设

以下是方向规划用的粗估，不是交付承诺。一个人日表示一名熟悉仓库的开发者完成约一天有效工作；
正式 3D 资产工时受建模、绑定与动画经验影响最大。估算不包含新增长篇剧情、大量装备、Boss、
随机词缀和正式音乐制作。

| 阶段 | 预计投入 | 可见结果 |
|---|---:|---|
| 阶段 0：方向与基准 | 2 至 4 人日 | G0 参数和迁移前基准 |
| 阶段 1：3D 灰盒 | 8 至 14 人日 | 可完整循环的即时战斗原型与 G1 报告 |
| 阶段 2：正式规则 | 10 至 16 人日 | 地图内 BattleSession、内容 schema、剧情与存档边界 |
| 阶段 3：素材管线 | 15 至 30 人日 | 基础人形、动画、敌人和环境模块的可重复管线 |
| 阶段 4：正式切片 | 12 至 20 人日 | 一段达到正式质量的 3D 战斗内容 |
| 阶段 5：地图生成器 | 15 至 25 人日 | 3D plan/validate/bake、Dock 和测试 |
| 阶段 6：三张地图迁移 | 20 至 40 人日 | 3D 正式基线、旧存档迁移和旧运行时清理 |

按单人连续投入估算：

- 2 至 3 周得到 G1 方向结论；
- 8 至 14 周得到第一个正式 3D 战斗切片；
- 16 至 30 周完成地图生成器和现有三张地图的正式迁移。

可以并行的只有边界清楚的工作，例如灰盒规则与摄影机验证、基础人形与环境模块。StoryContext、
MapGameScene、内容 schema 和存档迁移位于同一关键路径，不通过多人并行同时修改来压缩工期。

## 5. 目标运行时边界

### 5.1 保留的系统

以下概念继续作为稳定边界：

- GameRoot：应用级服务、Overlay、GameSceneStack 和当前 GameRun；
- GameSceneStack：标题、地图、菜单、商店和存档等完整场景流程；
- GameRun：队伍、背包、金钱、故事、标记、世界状态和位置；
- ContentDatabase：Actor、Item、Skill、Enemy、Encounter、Map 等静态定义；
- StoryContext：剧情调用对话、商店、战斗、奖励、来源完成和地图切换的公共 API；
- BattleSession：一次有限遭遇的临时规则状态；
- BattleActorState：本场战斗的 HP、MP、冷却、状态和生死；
- BattleEvent：规则层向表现层报告伤害、治疗、状态、动作和结果；
- BattleResult：把遭遇结果返回调用方并明确提交边界；
- GameEffect：有限、类型化的机械效果，不承担剧情和场景控制。

### 5.2 需要改变的系统

- `PlayerCharacter` 从 CharacterBody2D 迁移为 CharacterBody3D，但仍随 MapGameScene 创建和销毁。
- 地图 NPC、敌人、交互对象、CameraRig、spawn 和 persistent 来源迁移为 3D 节点。
- 普通战斗不再通过 `GameSceneStack.push(BattleGameScene)` 启动。
- MapGameScene 启动并拥有当前 BattleSession；BattleSession 结束后才释放战斗输入。
- `StoryContext.start_battle()` 保持相同的高层调用形式，底层委托当前 MapGameScene 并等待结果。
- BattleSession 从一次 `execute(command)` 一个回合，改为固定规则步长推进动作、冷却和状态。
- BattleActorView 不持有唯一规则数据，只表现 BattleActorState 与 BattleEvent。
- `rounds` 迁移为 `duration_msec`、`defeated_enemy_ids` 等实时战斗统计。
- 回合状态迁移为明确的秒数、固定 tick 或动作事件生命周期。

### 5.3 地图内遭遇生命周期

推荐生命周期：

```text
Dormant
  -> Alerted
  -> Active
  -> Victory / Escaped / Defeat
  -> ResultCommitted
  -> Disposed
```

- Dormant：敌群未警戒，探索与互动正常。
- Alerted：敌人发现玩家，建立 BattleSession 并切换战斗输入与 HUD。
- Active：实时推进动作；禁止保存、商店、菜单事务和新的独占 StoryEvent。
- Victory：全部必要敌人死亡，提交 HP/MP、消耗与 Encounter 奖励并完成来源。
- Escaped：玩家脱离追击和遭遇边界，只提交 HP/MP 与物品消耗，不完成来源。
- Defeat：提交 HP/MP 与消耗，StoryContext 调用方负责恢复与 terminal travel。
- ResultCommitted：提交操作必须幂等，重复结束信号不得重复奖励。
- Disposed：释放 BattleSession、敌人临时状态、HUD 和战斗输入，恢复正确的上层控制者。

自由地图敌人也必须属于一个有限 Encounter，不建立没有结束边界的全局战斗状态。

### 5.4 输入所有权

输入所有权保持单一：

- 探索：PlayerController 接收移动与互动输入。
- 战斗：同一个玩家化身接收移动、瞄准和战斗动作，互动与事务菜单禁用。
- StoryEvent：StoryDirector 持有控制锁；调用 `start_battle()` 时暂时把角色动作权交给当前
  BattleSession，BattleResult 返回后重新由 StoryDirector 持有，直至剧情结束。
- Dialogue：Overlay 模态输入优先，地图与战斗不消费输入。
- GameSceneStack push：底层地图暂停，不推进 BattleSession。

不得用全局 EventBus 协调这些模式。拥有者通过直接方法切换控制，子节点用 signal 报告已经发生的动作。

## 8. 风险登记

| 风险 | 早期信号 | 缓解 | 停止条件 |
|---|---|---|---|
| 3D 素材首件成本过高 | 基础人形与六动画长期无法稳定导入 | 降低模型细节、统一骨骼、减少动画数量 | 第二个变体仍无复用收益 |
| `640 x 360` 3D 闪烁 | 静止可读但移动时边缘持续跳动 | 简化轮廓、调整材质和摄影机尺度 | 仍无法稳定时评估更高根分辨率 |
| 战斗输入不适合手柄 | 瞄准与移动互相抢夺 | 分离移动/瞄准、增加迟滞和有限软锁定 | 两轮迭代后仍无法稳定选向 |
| 地图内战斗破坏剧情锁 | 战斗后输入无法恢复或剧情并发 | 直接所有权交接、单 BattleSession、场景级测试 | 出现无法可靠复现的并发状态 |
| 3D 地图生成范围失控 | 先重写工具、长期没有可玩切片 | G4 前手工搭小地图，生成器放在阶段 5 | 正式切片尚未成立就要求迁移全工具 |
| 暗黑式需求膨胀 | 开始增加词缀、品质、技能树和大量掉落 UI | 坚持第 3.3 节非目标，新增需求单独立项 | MVP 无法在有限敌人和技能下完成 |
| 旧存档位置不可映射 | 2D 坐标对应不到 3D 路径 | 保留语义 spawn，迁移时丢弃精确位置 | 不允许为了位置映射损坏其他进度 |
| 双运行时长期共存 | 原型和正式实现开始互相引用 | 原型不登记内容，G1 后迁移或删除 | 出现第二套 ContentDatabase 或保存协议 |

## 10. 交付与合并原则

- 每个阶段都要有可运行产物、验收记录和明确决策门。
- G1 前不修改默认入口、正式地图、ContentDatabase 和存档格式。
- 原型任务与正式迁移任务分开提交，不把临时胶囊体和正式内容混在一个变更中。
- 正式规则变更先有无窗口测试，再接入动画、VFX 和音频。
- 正式素材先通过导入校验，再进入 ContentDatabase 或地图场景。
- 地图逐张迁移，未通过完整剧情与存档验收的地图不替换当前正式入口。
- 只有所有运行时引用迁移完成后才清理旧实现，不通过删除旧基线来制造迁移进度。
